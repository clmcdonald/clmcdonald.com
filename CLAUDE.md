# CLAUDE.md — clmcdonald.com

Static React SPA served from Cloudflare. Two routes: a placeholder landing page
(`/`) and **Hearts** at `/hearts` (the actual application), a human against
three AI opponents, built to work on desktop, mobile web, and as an installed
PWA.

Workspace-wide conventions (shell, `fnm`, `ripgrep`, `ast-grep`, SDKMAN) live in
`~/dev/CLAUDE.md`. This file covers only this repository.

## Stack

React 19 (function components + hooks only) · TypeScript 6 · Vite 8 (Rolldown) ·
TanStack Router (file-based) · styled-components 6 · Yarn 4 · Vitest ·
Cloudflare static hosting.

## TypeScript constraints that will break your build

`strict` is **not** written in `tsconfig.app.json`, but TypeScript 6 defaults it
on — so implicit `any`, unchecked `null`, and the rest all error regardless. Do
not "fix" this by adding the flag; it is already in effect.

Beyond that, three flags in `tsconfig.app.json` shape the code you may write:

- **`verbatimModuleSyntax: true`** — type-only imports must use `import type`.
  A plain `import { Card }` for a type is an error.
- **`erasableSyntaxOnly: true`** — **`enum` is forbidden.** Use a string-literal
  union with a sibling `as const` array (see `domain/types.ts` for `PlayerId`,
  `Suit`, `Difficulty`).
- **`noUnusedLocals` / `noUnusedParameters`** — dead locals and unused params
  are errors, not warnings. Prefix intentionally-unused params with `_`.

Formatting is enforced by Prettier via `lint:ci`: single quotes, semicolons,
2-space indent, 80 columns, `trailingComma: 'es5'` — note the last one means
**no** trailing comma after a function's final parameter, but yes after object
and array entries.

## Architecture

```
src/
  main.tsx            createRoot + RouterProvider + SW registration
  routes/             file-based routes; __root.tsx holds GlobalStyle + Outlet
  pwa/registerSW.ts   production-only service-worker registration
  features/hearts/
    domain/           pure game logic — no React, no DOM, no I/O
      types.ts        all shared types
      deck.ts         deck, seeded RNG, shuffle, deal
      rules/          cards · passing · tricks · scoring · validate
      ai/strategy.ts  opponent play
      engine/         reducer.ts (the state machine) · simulate.ts · index.ts
    state/            useHeartsGame.ts (the hook) · storage.ts (localStorage)
    components/       React rendering layer
    styled.ts         all styled-components for the feature (~900 lines)
    __tests__/
```

**The dividing line is `domain/` versus everything else, and it is load-bearing.**
`domain/` is pure TypeScript: no React import, no `localStorage`, no `Date`, no
ambient randomness (`Math.random`), no timers. All randomness enters as an
integer seed carried in `GameState`, so any game is reproducible from its seed —
that is what makes the engine testable and replayable.

Consequences to respect:

- `domain/` functions are deterministic and side-effect free. `reduce(state,
action)` returns a new state; it never mutates or reads the world.
- Anything involving _time_ — AI thinking delays, how long a trick stays on the
  table, animation pacing — belongs in `state/useHeartsGame.ts` as a constant
  plus a `useEffect` with a timer, **never** in `domain/`.
- `localStorage` access is confined to `state/storage.ts`. It validates and
  truncates everything it reads; a stored value is untrusted input.
- Two deliberate exceptions, both confined and both fine: `defaultSeed()` in
  `engine/reducer.ts` falls back to `Date.now()` only when `crypto` is
  unavailable (the value is stored in state, so determinism is preserved), and
  `useHeartsGame.ts` uses `globalThis.crypto` for the initial seed.
- `engine/simulate.ts` (`step`/`playFullGame`) drives the reducer without timers
  so tests can play thousands of complete games. **If you add a new phase or a
  new "waiting" state to the reducer, you must teach `simulate.step` to walk
  through it** — otherwise the fuzz tests will spin or fail.

React is a thin rendering layer. Keep game decisions out of components; if a
component needs to know a rule, the rule already lives in `domain/rules/`.

## Testing

`vitest.config.ts` sets `environment: 'node'`. There is **no jsdom, no
@testing-library, no DOM** — install nothing that assumes one without saying so.

- Engine and rule tests (`engine.test.ts`, `rules.test.ts`) drive `reduce`
  directly with seeds and assert on state.
- Component tests (`render.test.tsx`) are **`renderToStaticMarkup` string
  assertions** — smoke tests that the tree renders from a real engine state and
  that key content reaches the markup. They do not test layout or interaction.
- `storage.test.ts` stubs `window` by hand with an in-memory `Map` rather than
  pulling in jsdom for one module. Follow that pattern.
- `components/demoState.ts` builds states for component tests by driving the real
  engine and stopping at a chosen point (`createDemoState`,
  `createResolvedTrickState`); use it rather than hand-writing a `GameState`,
  which the type system will punish anyway. Its private `drive(seed, stop)` is
  the general form — export a new named helper rather than loosening it.

### The fuzz test cannot catch a wrong rule

`legalPlays` in `domain/rules/validate.ts` is the single legality gate — the
reducer enforces with it, the AI chooses from it, and the UI highlights from it.
That is the right design, but it makes the rules fuzzing test ("only ever plays
legal cards") **self-referential**: it asks "was this play in `legalPlays`?" and
takes `legalPlays` as the oracle, so it agrees with itself no matter how a rule
is encoded. It stayed green for a while with the 2♣ opening lead wrongly applied
to the game's first hand only.

So any rule whose content matters needs a second assertion derived from the rules
text rather than from `legalPlays` — recompute the led suit, the highest card,
the trick winner and who leads next from the played cards, and assert on those.
`engine.test.ts` has such an audit ("follows the rules of Hearts, judged
independently of legalPlays"); extend it when you touch a rule. When you fix a
rule, **confirm the new test fails against the old logic** — a regression test
that passes either way is worthless, and the check is cheap (edit, run, revert).

### Verifying visual changes

There is **no browser automation** on this machine — no Playwright, Puppeteer,
Cypress, jsdom or happy-dom, and geckodriver is not installed — so there is no
way to click through the app. What you _do_ have:

- **SSR markup assertions** (`render.test.tsx`). styled-components encodes props
  into the generated class name, so two renders styled differently differ in the
  markup — that is how a styling prop can be tested from a string render.
- **Grepping the built bundle** (`dist/assets/*.js`) to confirm CSS was emitted.
  This proves a string is present, **not that the browser accepted it**: a
  declaration the CSS parser rejects still appears verbatim in the bundle. See
  the animation-shorthand trap under Styling.
- **Headless Firefox screenshots**, which do work here and are the way to check
  layout and animation:

  ```
  mkdir -p /tmp/shot && firefox --headless --no-remote \
    --profile /tmp/shot --screenshot out.png --window-size=1400,900 "$URL"
  ```

  The profile directory **must exist first** or Firefox exits with "Could not
  find profile folder", and a **separate profile is mandatory** while the user's
  own Firefox is running. It is flaky — retry two or three times and treat a
  missing PNG as a failed run, not an empty page. A continuously mutating DOM
  (a persistent `requestAnimationFrame` loop) can prevent capture entirely.

To drive a real game state into a screenshot, render the real components from
`components/demoState.ts` in a throwaway entry point rather than screenshotting
the app shell. To photograph a **CSS animation**, do not race the capture:
freeze it first with the Web Animations API and read back the computed geometry.

```js
for (const a of document.getAnimations()) {
  a.pause();
  a.currentTime = 900; // ms, delay included
}
```

`document.getAnimations()` returns an empty list during the first tick, because
React commits asynchronously and CSS animations are only created by the style
flush that follows. Pin inside a `useLayoutEffect` (which runs before the first
paint) — a `setTimeout(…, 0)` fires too early to find anything. Read back
`getComputedStyle(el).transform`, `opacity` and `getBoundingClientRect()` to get
numbers you can assert on instead of eyeballing pixels. When the values at
several `currentTime`s agree across repeated samples, the pin is real.

- **Reading the pixels.** A screenshot tells you a colour is there; sampling the
  PNG tells you which one. There is no ImageMagick here, but a PNG is only zlib
  plus a per-scanline filter, so a ~60-line Node script (`inflateSync` and the
  five filter modes) will print the RGB at any coordinate. That is how the felt
  was shown to start at exactly the theme colour, and that the vignette below it
  is still painted rather than silently dropped. A scratch one lives at
  `/tmp/hearts-vis/png.mjs` — recreate it if the temp dir is gone.
- **A throwaway harness has to reproduce the app's reset.** `__root.tsx` sets
  `body { margin: 0 }`; a harness that renders the real components without it
  measures everything 8px out, and each seat column loses 16px of width — enough
  to make a seat header wrap that does not wrap in the app. Check the harness
  against a screenshot of the app before trusting a difference it reports.

Note that some visual QA still cannot be automated away — say plainly that human
review is outstanding when it is. A layout that fits the viewport in a headless
Firefox window is not proof that it fits an iPhone: the status bar and home
indicator take `env(safe-area-inset-*)` off the top and bottom, and the system
font is not the one Firefox has.

## Styling

All styled-components for a feature live in its single `styled.ts`. Transient
props are `$`-prefixed (`$dimmed`, `$selected`, `$winner`) so they are not
forwarded to the DOM.

Two traps specific to this file:

- **Never put a backtick anywhere inside a CSS comment.** The whole file is a
  styled-components template literal, so a stray `` ` `` — even in prose, even
  inside a `/* */` comment — terminates the CSS string. This breaks lint, tests
  and build at once, and the reported location is usually the token _after_ the
  real one, so the error points somewhere innocent. In the dev server it is
  worse than an error: Vite serves a tiny error-overlay module instead of the
  page and the app silently renders nothing. Write `inset: 0` in prose, never
  wrapped in backticks.
- **Restarting a CSS animation requires changing the `animation` property on the
  element.** A fly-out animation and an entry animation therefore cannot share an
  element, because re-rendering restarts whichever one is attached. The trick
  cards split these across a wrapper and an inner element for exactly this
  reason.

And one trap that is not about this file's syntax but cost a lot of debugging:
in the `animation` **shorthand**, each component may appear only once. Writing
`animation: X 660ms ease 340ms forwards backwards` is invalid, so the browser
throws away the **entire declaration** — the element simply never animates, with
no console warning, while the keyframes sit in the sheet unused and the text
still appears in the built bundle. The combined keyword is `both`. If an
animation will not play, check `getComputedStyle(el).animationName`: `none`
against a correctly-spelled `animation` rule means the shorthand was rejected.
`document.getAnimations()` will not list it either, since no animation was ever
created.

Note also that `inset: 0` on an absolutely positioned pseudo-element resolves
against the ancestor's **padding box**, not its border box. An overlay meant to
cover a bordered element needs a negative inset of one border width.

`src/routes/hearts.tsx` sets the page background (felt green `#0d5c2e`) via a
route-scoped `createGlobalStyle`; `__root.tsx` owns the global reset.

The felt's vignette (**`Container`**) starts on a band of flat `#0d5c2e` and only
begins darkening below it. That is not decoration: the installed PWA's status
bar is painted the same green over the top of the page, so a gradient that is
already partway to `feltDark` at zero height leaves a visible seam across the top
of the screen. Keep the theme colour the first stop of the first layer.

**Fan spacing is derived from the width of the row, never fixed.** `HandRow` and
`CardFan` both lap their cards by

```css
calc(
    min(calc(var(--card-w) * 0.58), calc((100% - var(--card-w)) / (n - 1))) -
      var(--card-w) - 1px
  )
```

— the spacing a fan wants, or the most the row can lend it, whichever is less, so
the fan always fits and stays as open as it can (the trailing pixel is slack
against sub-pixel rounding, which would otherwise leave the row scrolling by a
hair). A fixed fraction of a card
cannot do this: thirteen cards at a fixed lap are half again as wide as a phone
screen, which is what made the hand scroll and the opponents' fifth card hang off
the edge. `n - 1` is the number of gaps; `CardFan` takes it as a prop, because a
divisor cannot be a CSS variable. `CardFan` also stops at five backs — thirteen
slivers inside one seat render as a hatched block rather than a hand of cards —
so the number beside the seat name, never the fan, is what states the count.

`TableArea` keeps the compass at every width — west left, north above, east
right, you at the foot — and only the column widths change. Below 900px the
middle column narrows to exactly the trick cross (`--cross-w`, three cards plus
two `--trick-gap`s) and the two side seats take what is left: about 91px each at
390px, where the seat header wraps to two lines and the derived fan lap closes
the backs right up. Sharing the middle column was also what left the hand room
for six of its thirteen cards, so the hand gets a full-width row of its own.

The pass bar cannot live in that column either — it needs nearly the whole
screen to stay on one line — so it has a row of its own between the table and
the hand. `Table` renders its children into `NoticeArea` for that; moving them
back inside `CenterArea` silently crushes the bar on a phone.

North spans the whole top row and is then held to the width its neighbours get:
`calc((100% - var(--cross-w) - var(--table-gap) * 2) / 2)`. A spanning item
resolves that `100%` against the sum of its three columns _and_ the gaps between
them, so the result is the side column's width at any viewport, with no
viewport units anywhere. Note it has to be `width`, not `max-width`: with
`justify-self: center` a seat sizes to its own text, so a looser `max-width`
does not bind at all and north's fan comes out _narrower_ than the other two —
which is exactly what happened on a tablet.

## PWA

`public/sw.js` is a hand-written service worker (not a Workbox/generated one),
registered only in production (`src/pwa/registerSW.ts`). It precaches the app
shell plus the hashed bundles scraped out of the built HTML, serves `/assets/`
cache-first, and navigations network-first with a cached fallback.

**Bump `CACHE_NAME` when you ship a change**, or clients keep serving the old
shell. Note it is excluded from the TypeScript project and linted with
service-worker globals (see the `public/**/*.js` block in `eslint.config.js`).

Each route declares its own favicons and manifest in its `head()` — deliberately
client-side rather than in `index.html`, so the site root is not installable as
Hearts. Do not hoist a manifest into `index.html`.

## Deployment

Cloudflare builds from `master`; commits to the default branch deploy
automatically. `public/_redirects` (`/*  /index.html  200`) provides SPA
fallback. The default branch is `master`, not `main`.

CI (`.github/workflows/pr-checks.yml`) runs against PRs into `master` on **Node
20** and runs `yarn install --immutable`, `lint:ci`, `test`, `build`. Local is
Node 24, so do not introduce anything that depends on a newer Node than 20.

Dependabot opens weekly dependency PRs against `master`.

## Git

Commit or push only when asked. If you are on `master`, branch first. Releases
of a new service-worker shell require the `CACHE_NAME` bump described above.

`.husky/pre-commit` runs `lint-staged`, which applies `eslint --fix` and
`prettier --write` to staged files — so a commit can silently rewrite what you
staged. Re-check `git diff` after committing rather than assuming the working
tree still matches what you reviewed.
